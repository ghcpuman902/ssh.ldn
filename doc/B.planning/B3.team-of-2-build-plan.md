# B3.team of 2 build plan

Plan for building `ssh.ldn` with two people at Londonmaxxing.

## Position

You can build the app solo, so a second person should not create process drag. The team-of-two version only makes sense if work is separated into independent data/map layers that can be merged late without constant collisions.

Best split:

- **You**: product direction, core app shell, scoring contract, UX/design, final merge, pitch.
- **Teammate**: data-source layers as independent adapters and map overlays.

The key rule is:

> Every data source becomes a layer with the same interface.

That means each layer can be tested alone, visualised alone, then merged into the score only after it works.

## Shared Architecture

Use one common layer contract:

```text
test point or coordinate
  -> source adapter
  -> normalised features
  -> optional map layer
  -> evidence rows
  -> score contribution
```

Each layer should return:

- `sourceId`
- `sourceName`
- `status`
- `features`
- `evidenceRows`
- `warnings`
- `mapLayer`
- `scoreContribution`
- `confidenceContribution`

This prevents collisions because one person can improve the app shell while the other adds layers behind a stable boundary.

## Team Rules

- One person owns the app shell and design system.
- One person owns data adapters and map overlays.
- Do not both edit the same component unless pairing.
- Put each data source in its own file.
- Put sample outputs in source-specific JSON files.
- Merge source outputs through one aggregator, not directly inside UI components.
- By 15:00, stop building separate features and merge.
- By 15:45, stop adding sources and improve design/reliability.

## High-To-Low Impact Data Source Checklist

Use this as a shared time-control board. Person B owns discovery and adapters; Person A decides when the UI has enough.

- [ ] **Seeded test-point JSON**: must exist first so the UI and demo are never blocked by APIs.
- [ ] **Geocoding**: required for search, map placement, and all source queries. Use Postcodes.io as fallback and address-grade lookup if available.
- [ ] **OSM Overpass local features**: best teammate-owned layer because it returns visible map markers for pubs, nightclubs, roads, rail and buildings.
- [ ] **DEFRA road noise**: highest official impact; gives the strongest noisy-versus-quiet contrast. Map layer: WMS tiles — see [B4.london-noise-map-sources.md](./B4.london-noise-map-sources.md).
- [ ] **DEFRA rail noise**: strong if easy to sample; useful for King's Cross and rail context. Pair with OSM **overground-only** line geometry (exclude `tunnel=yes`, `subway`).
- [ ] **DEFRA airport noise**: use if query/sampling path is clear; otherwise keep aircraft as a caveat, not a fake score. Optional Heathrow DXF contour polygons for map.
- [ ] **TfL Unified API**: good second-person enrichment for station/line context and London specificity.
- [ ] **DfT road traffic statistics**: useful explanatory backup for road intensity, but skip if nearest-neighbour matching takes too long.
- [ ] **Planning London Datahub / planning.data.gov.uk**: future disruption layer; only add if core score and map already work.
- [ ] **OpenRouter explanation**: add after deterministic evidence exists. Keep fallback copy for all four test points.
- [ ] **AG Grid evidence table**: worthwhile if Person B generates many evidence rows; otherwise a simple evidence list is faster.
- [ ] **ElevenLabs ambient sound preview**: strong product differentiator on contributor hover; see [Ambient sound preview](#ambient-sound-preview-elevenlabs). After 15:00 only if core score/map is stable.
- [ ] **ElevenLabs voice narration**: optional accessibility polish; lower priority than sound preview.
- [ ] **TRMNL**: skip unless sponsor demo opportunity is unusually strong and core app is done.
- [ ] **London Air / Breathe London / Police / Land Registry / EPC / ONS**: defer; useful context but not central to acoustic regret.

## Ambient sound preview (ElevenLabs)

A strong ElevenLabs use case is not only voice narration, but **sound preview**.

When a user hovers over a noise contributor, the app could play a short generated ambient clip:

- pub garden chatter
- railway pass-by
- Underground rumble
- aircraft overhead
- siren corridor
- construction drilling
- night traffic
- football crowd

This changes the product from an abstract score into an embodied experience.

Instead of only saying:

> Rail noise: high

the interface lets the user briefly hear what that risk might feel like.

This is especially useful because people often misunderstand decibel numbers. A 65 dB road, a 65 dB pub garden, and a 65 dB railway pass-by can feel very different because of rhythm, frequency, duration, and predictability.

The sound preview must not claim to be an exact simulation. Label it clearly as:

> Representative sound preview

or:

> Example sound texture, not measured audio.

Possible interaction:

- hover on contributor bar to preview sound
- click to lock playback
- slider for estimated intensity
- day/night toggle changes ambience
- accessibility option: textual sound description for users who do not want audio

This makes ElevenLabs feel native to the product rather than bolted on.

**Ownership:** Person A (contributor bar + playback UX). Person B maps contributor types to preview textures in evidence rows if needed.

**Timing:** only after 15:00 merge freeze candidate — do not block core score or fallback JSON.

**Pitch beat:** optional demo moment on Fabric (night traffic / crowd) or Euston (rail + road stack).

## Merge Rules

Merge only through the aggregator:

```text
testPoint
  -> run enabled source layers
  -> collect normalised layer results
  -> compute score/confidence
  -> render UI
```

Do not allow:

- source-specific fetch logic inside visual components;
- raw API response fields inside scoring;
- one layer to throw and break the whole result;
- hidden manual edits that are not captured in fallback JSON.

## When Team Of Two Is Better Than Solo

Team of two is worth it if:

- setup is complete before 10:15;
- the teammate can own data layers independently;
- each source becomes a visible map/evidence layer;
- you keep final authority over product and design;
- the team reserves real merge time.

Stay effectively solo if:

- environment setup drags past 10:30;
- the teammate wants to co-edit the same UI;
- source work produces research notes but no normalised layer output;
- merge risk becomes larger than data benefit.

## Final Team Deliverable

By 16:00, aim to have:

- independent source layers;
- visible map markers or overlays;
- score, source breakdown, time profile, confidence, and caveats;
