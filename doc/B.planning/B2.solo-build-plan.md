# B2.solo build plan

Plan for building `ssh.ldn` alone at Londonmaxxing.

## Position

You can build the app solo. The advantage is speed, taste, fewer merge conflicts, and one coherent product vision.

The risk is trying to prove too many datasets before the demo. The solo plan should therefore optimise for one complete vertical slice:

```text
address input
  -> coordinates
  -> local evidence bundle
  -> noise score
  -> map/result page
  -> explanation
  -> fallback demo data
```

Do not start with a beautiful generic map. Start with data that makes the four test points tell clearly different stories.

## Solo Strategy

Build in this order:

1. Hard-code the four test points.
2. Make the app render one full result from static JSON.
3. Add geocoding.
4. Add one high-impact local data layer at a time.
5. Freeze the score contract.
6. Improve the result page design.
7. Rehearse the pitch inside the product.

The product should still work if every external endpoint fails during the demo. Live data is proof of engineering; fallback data is proof of judgement.

## Time Plan

### 09:00-10:00: Arrive, settle, and reduce uncertainty

Use breakfast/networking time lightly, but protect your setup.

- Confirm WiFi, power, deployment account, env vars, and API keys.
- Open the project, run install/check commands only if needed.
- Create or verify `.env.local` values.
- Keep a note of any source that needs signup or has a brittle API.
- Decide whether to stay solo or team up before 10:15.

Output:

- repo ready;
- deploy path known;
- four test addresses copied into a seed file;
- no mystery dependencies.

### 10:00-10:30: Opening talks and scope lock

Listen for sponsor/judging details, then lock the MVP.

MVP promise:

> Paste a London address and understand whether the home is likely to be noisy, why, when, and how certain we are.

Hard scope:

- four test-point demos;
- one search/result flow;
- one map;
- one score card;
- one source breakdown;
- one time-of-day profile;
- one explanation panel.

No-go unless everything else works:

- real 3D acoustic simulation;
- ElevenLabs sound preview or voice narration;
- TRMNL;
- live planning data;
- advanced animation;
- multi-address comparison.

### 10:30-11:15: Static vertical slice

Build the result page from local JSON before connecting APIs.

The static JSON should include:

- address;
- coordinates;
- noise score;
- confidence;
- contributor weights;
- day/evening/night values;
- evidence rows;
- caveats;
- recommended checks.

Success:

- switching between the four test points visibly changes the UI;
- the story is obvious even before live endpoints work.

### 11:15-12:00: Geocoding and map placement

Implement address lookup and map positioning.

Priority:

1. Full-address geocoder if already available.
2. Postcodes.io for postcode fallback.
3. Manual seeded coordinates for demo fallback.

Success:

- every test point has coordinates;
- coordinate precision appears in confidence scoring;
- map works from either live geocode or fallback JSON.

### 12:00-13:00: Highest-impact data layers

Add only the data sources that create visible differentiation.

Use the checklist below. Stop as soon as the four stories are clear enough.

Output:

- local evidence bundle per test point;
- consistent fields;
- no source blocks the whole app.

### 13:00-14:00: Lunch and recovery

Do not deep-code through lunch unless the app is broken.

During lunch:

- test the deployed URL;
- write the 60-second pitch skeleton;
- decide what gets cut;
- check the four demo addresses on the live build.

### 14:00-15:00: Score, confidence, and explanation

Freeze the internal score response.

The score should be deterministic:

```text
official baseline first
  + local source proxies
  + temporal modifiers
  + confidence penalties
```

Explanation should be generated from structured evidence only. If LLM output is brittle, use approved fallback copy.

Success:

- Euston Road ranks noisy;
- Fulham ranks quieter;
- Fabric has elevated night risk;
- Wapping has pub/local context and aircraft caveat where defensible.

### 15:00-15:45: Design pass

This is where solo advantage matters.

Polish the product so judges understand it without a lecture:

- large headline score;
- clear confidence badge;
- map with visible source layers or markers;
- stacked contributor bar;
- day/evening/night profile;
- plain-English caveats;
- "what to check before signing" recommendations.

Do not redesign the whole app. Improve hierarchy, spacing, contrast, and copy.

### 15:45-16:00: Freeze

Stop adding data.

Final actions:

- ensure fallback JSON works;
- deploy;
- save URL;
- rehearse exact demo path;
- close risky tabs/tools.

### 16:00-17:30: Pitch window

Use the product as the presentation.

Demo order:

1. Open with the renter problem.
2. Show Euston Road as noisy.
3. Show Fulham as quiet contrast.
4. Show Fabric as time-dependent night risk.
5. Show evidence/confidence so it feels trustworthy.

## High-To-Low Impact Data Source Checklist

Use this as the time-control list. Move down only when the current item is working and visible in the product.

- [ ] **Seeded test-point JSON**: highest practical impact because it guarantees the demo and gives the UI a stable contract.
- [ ] **Geocoding**: required for address search and map placement. Use Postcodes.io fallback if address-grade lookup is slow.
- [ ] **OSM Overpass local features**: fastest way to show pubs, bars, nightclubs, roads, rail, buildings, and local explanation.
- [ ] **DEFRA road noise**: strongest official baseline for the Euston Road versus Fulham contrast.
- [ ] **DEFRA rail noise**: important for King's Cross and rail/station context, but do not overclaim Underground vibration.
- [ ] **DEFRA airport noise**: useful for aviation context, especially if Wapping/Heathrow path can be represented defensibly.
- [ ] **TfL Unified API**: good London-specific enrichment for stations, lines, and service context; not core if time is short.
- [ ] **DfT road traffic statistics**: helpful explanatory proxy for major roads, but less important if DEFRA road is working.
- [ ] **Planning London Datahub / planning.data.gov.uk**: future disruption card only; skip if score or UI is unfinished.
- [ ] **OpenRouter explanation**: valuable polish once deterministic evidence exists; fallback copy is acceptable.
- [ ] **AG Grid evidence table**: useful if many source rows exist; otherwise simple cards are faster and cleaner.
- [ ] **ElevenLabs ambient sound preview**: hover contributor bar to hear representative textures (pub, rail, aircraft, etc.); not measured audio — see B3 team plan for full interaction spec.
- [ ] **ElevenLabs voice narration**: optional accessibility polish; lower priority than sound preview.
- [ ] **TRMNL**: ambient dashboard idea; not needed for the core pitch.
- [ ] **London Air / Breathe London / Police / Land Registry**: broader liveability context; likely scope creep for this build.

## Cut Rules

Cut a source if:

- it needs signup and is not available within 10 minutes;
- it cannot be queried for all four test points;
- its output cannot be explained to a judge in one sentence;
- it does not change the UI or scoring visibly;
- it risks breaking the demo path.

## Final Solo Deliverable

By 16:00, aim to have:

- a live URL;
- four working demo addresses;
- a deterministic fallback path;
- a polished result page;
- source breakdown and confidence;
- a short explanation per address;
- a pitch that starts with human regret, not decibel modelling.
