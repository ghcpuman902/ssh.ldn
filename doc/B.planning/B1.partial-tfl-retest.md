## 1. TfL nearby stops — `/api/discovery/tfl/nearby-stops`

**Status: FAIL** (unchanged)

### Input validation — pass

```bash
curl "http://localhost:3999/api/discovery/tfl/nearby-stops?lat=bad&lng=bad"
```

HTTP **400** — `{"error":"lat and lng are required numbers"}`

### Test points — all fail (upstream 404)

| testPointId | lat | lng | HTTP | result | latency |
|-------------|-----|-----|------|--------|---------|
| `kings_cross_euston_road_noisy` | 51.5308 | -0.1238 | 502 | TfL 404 | ~34 ms |
| `fabric_day_night_pattern` | 51.5202 | -0.1017 | 502 | TfL 404 | ~30 ms |
| `wapping_pub_quiet_aircraft` | 51.5043 | -0.0586 | 502 | TfL 404 | ~30 ms |
| `fulham_residential_quiet` | 51.4689 | -0.2108 | 502 | TfL 404 | ~30 ms |

Example response:

```json
{"error":"TfL API request failed: 404 Not Found"}
```

### Direct upstream verification (with credentials from `.env.local`)

All return `{ "statusCode": 404, "message": "Resource not found" }`:

| Endpoint | HTTP |
|----------|------|
| `GET /StopPoint?location.lat=…&location.lon=…&radius=500&stopTypes=…` | 404 |
| `GET /StopPoint?…&stopTypes=NaptanMetroStation&stopTypes=NaptanRailStation` (multi) | 404 |
| `GET /Place?placeGeo.lat=…&placeGeo.lon=…&radius=500` | 404 |

**Working alternative (name search, not geo radius):**

```bash
GET /StopPoint/Search?query=Kings%20Cross
```

HTTP **200** — returns matches with `id`, `name`, `lat`, `lon`, `modes`.

### Root cause

TfL geo lookup endpoints appear deprecated or broken on TfL's side. Retesting with newly added `TFL_APP_ID` / `TFL_APP_KEY` did **not** resolve the 404. Line status and StopPoint search both work with the same credentials, confirming keys are valid.

### Minimal fix attempted

No local code change applied — upstream 404 cannot be fixed by credential rotation or parameter tweaks alone. Recommended next step (out of scope for this retest): implement `stopPoint.search` fallback keyed by geocoder place name, or defer TfL stops as optional enrichment per B1 guidance.
