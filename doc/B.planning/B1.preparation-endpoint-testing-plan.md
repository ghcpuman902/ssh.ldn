# B1.preparation: endpoint testing plan

Hackathon preparation plan for tomorrow.

## Preparation Scope

This endpoint/API discovery work is allowed ahead of the hackathon. Treat it as curiosity-driven preparation, not final product building: make the smallest useful server helper and local API endpoint, test it with `curl`, learn from the real response or error shape, then adjust.

The goal is quick feedback. Do not write a large integration layer first and discover late that the API shape, authentication, rate limit, coordinate format, or error response is different from expected.

## Goal

Validate every endpoint and data source needed to generate localised, mergeable property-noise data for the MVP.

The purpose is not to build the final UI first. The purpose is to prove that, for a given London address, the app can consistently produce one merged local evidence bundle with enough fields to power:

- address search;
- map placement;
- noise score;
- day/evening/night profile;
- source breakdown;
- confidence score;
- explanation text;
- demo fallback JSON.

## Discovery Loop

For each source, repeat this small loop:

1. Pick one test point, usually `kings_cross_euston_road_noisy` because failures are easy to see.
2. Implement one reusable server-side helper in `lib/server/<source>.ts`.
3. Import that helper into one thin `app/api/discovery/<source>/route.ts` handler.
4. Run one `curl http://localhost:3999/...` request against the user's already-running dev server.
5. Inspect the JSON shape, warnings, HTTP status, latency, and missing fields.
6. Update the helper/schema/endpoint, then try the next test point.

Keep scripts and endpoints short. A useful five-minute test is better than an untested full abstraction.

Recommended reusable pattern:

```ts
// lib/server/tfl.ts
import TflClient from "tfl-ts";

const tfl = new TflClient({
  appId: process.env.TFL_APP_ID,
  appKey: process.env.TFL_APP_KEY,
  timeout: 8000,
  maxRetries: 1,
});

export type NearbyTflStopsInput = {
  lat: number;
  lng: number;
  radiusMeters?: number;
};

export const getNearbyTflStops = async ({
  lat,
  lng,
  radiusMeters = 500,
}: NearbyTflStopsInput) => {
  const response = await tfl.stopPoint.getByGeoPoint({
    lat,
    lon: lng,
    radius: radiusMeters,
    returnLines: true,
  });

  return {
    source: "tfl",
    sourceEndpoint: "tfl.stopPoint.getByGeoPoint",
    radiusMeters,
    stopPoints: response.stopPoints ?? [],
  };
};
```

```ts
// app/api/discovery/tfl/nearby-stops/route.ts
import { type NextRequest } from "next/server";

import { getNearbyTflStops } from "@/lib/server/tfl";

export const GET = async (request: NextRequest) => {
  const lat = Number(request.nextUrl.searchParams.get("lat"));
  const lng = Number(request.nextUrl.searchParams.get("lng"));
  const radiusMeters = Number(
    request.nextUrl.searchParams.get("radiusMeters") ?? 500
  );

  if (!Number.isFinite(lat) || !Number.isFinite(lng)) {
    return Response.json({ error: "lat and lng are required numbers" }, { status: 400 });
  }

  const data = await getNearbyTflStops({ lat, lng, radiusMeters });

  return Response.json(data);
};
```

Use this shape for every source: route handlers parse HTTP input and return JSON; server helpers do the data-source work and remain reusable when building the actual scoring pipeline.

## Endpoint Test Matrix

Candidate endpoints:

- **Production:** Google Geocoding API (`GOOGLE_API_KEY`, server-side) — address-grade lookup for MVP.
- Postcodes.io for postcode centroid fallback.
- OS Places if a key becomes available (optional; Google covers production path).

Discover:

- Which endpoint can resolve full addresses, not just postcodes.
- Whether the endpoint returns enough precision for property-level testing.
- Rate limits, key requirements, licence constraints, and failure shape.

Confirm:

- Each test address resolves to a latitude and longitude.
- The returned location is close enough to the real frontage/building.
- The endpoint exposes precision metadata or a way to infer precision.
- Postcode fallback is clearly labelled as lower confidence.

Test:

- Run all four test points.
- Save raw responses.
- Compare coordinates on a map.
- Record `coordinatePrecision` as `exact_address`, `building`, `street`, `postcode`, or `unknown`.
- Confirm the app can continue when only postcode-level coordinates are available.

- official road/rail/airport baseline fields;
- OSM local features;
- optional TfL context;
- optional road-traffic intensity;
- optional planning/future disruption;
- final score;
- final confidence;
- explanation-ready evidence rows;
- raw-response references.

Merge validation:

- Coordinates use the same CRS internally, preferably WGS84 for app data.
- Distances are recomputed locally from the final coordinate, not trusted blindly from external APIs.
- All source rows include provenance and retrieval time.
- Missing data is represented as `null` plus a warning, not as zero.
- `null` means unknown; `0` means confirmed zero or no detected contribution.

## Definition Of Done

B1 preparation is complete when:

- all four test points have coordinates;
- every P0 endpoint has a documented success/failure result;
- each endpoint has required fields listed and mapped;
- each discovery endpoint has at least one saved `curl http://localhost:3999/...` command and observed response shape;
- reusable server-side helpers exist separately from thin route handlers;
- at least one merged local evidence bundle exists per test point;
- fallback JSON is ready for the demo;
- the score endpoint can produce the expected relative ranking;
- known caveats are visible in the data, not hidden in memory.
