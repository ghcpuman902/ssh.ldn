## 1. Raw curl vs tfl-ts — geo endpoints (all fail upstream)

Test coordinate: King's Cross (`51.5308`, `-0.1238`), radius `500 m`.  
Credentials appended as `app_id` / `app_key` (values redacted below).

### 1a. `GET /StopPoint?location.lat=…` (comma-separated stopTypes)

```http
GET https://api.tfl.gov.uk/StopPoint
  ?location.lat=51.5308&location.lon=-0.1238&radius=500
  &returnLines=true
  &stopTypes=NaptanMetroStation,NaptanPublicBusCoachTram,NaptanRailStation
  &app_id=…&app_key=…
```

| Layer | HTTP | Body |
|-------|-----:|------|
| **Raw curl** | 404 | `{ "statusCode": 404, "message": "Resource not found" }` |
| **tfl-ts** `stopPoint.getByGeoPoint` | 404 | `TfL API request failed: 404 Not Found` |

tfl-ts maps `{ lat, lon }` → query keys `location.lat`, `location.lon`, `stopTypes` (from `stoptypes` option). Same URL shape as raw curl.

### 1b. `GET /StopPoint?location.lat=…` (multi stopTypes param)

```http
GET …/StopPoint?…&stopTypes=NaptanMetroStation&stopTypes=NaptanPublicBusCoachTram&stopTypes=NaptanRailStation
```

| Layer | HTTP | Body |
|-------|-----:|------|
| **Raw curl** | 404 | `{ "statusCode": 404, "message": "Resource not found" }` |

OpenAPI specifies `collectionFormat: multi`; multi-param curl also 404s — serialization is not the root cause.

### 1c. `GET /Place?placeGeo.lat=…` (radius search)

```http
GET https://api.tfl.gov.uk/Place
  ?placeGeo.lat=51.5308&placeGeo.lon=-0.1238&radius=500
  &app_id=…&app_key=…
```

| Layer | HTTP | Body |
|-------|-----:|------|
| **Raw curl** | 404 | `{ "statusCode": 404, "message": "Resource not found" }` |
| **tfl-ts** `place.getByGeo` | 404 | (same upstream; not used in app) |

### 1d. `GET /Place` (bounding box)

```http
GET https://api.tfl.gov.uk/Place
  ?placeGeo.swLat=51.52&placeGeo.swLon=-0.13
  &placeGeo.neLat=51.54&placeGeo.neLon=-0.11
  &app_id=…&app_key=…
```

| Layer | HTTP | Body |
|-------|-----:|------|
| **Raw curl** | 404 | `{ "statusCode": 404, "message": "Resource not found" }` |

**Verdict:** TfL geo lookup endpoints are broken or deprecated upstream. Not a `tfl-ts` bug.

## 3. Fallback implementation

Because geo endpoints remain 404, `lib/server/tfl.ts` now:

1. Tries `tfl.stopPoint.getByGeoPoint` first (will succeed automatically if TfL restores geo).
2. On 404 only, falls back to `tfl.stopPoint.search` when:
   - `searchQuery` (or alias `query`) is provided, **or**
   - `testPointId` matches a seeded map:

| testPointId | searchQuery used |
|-------------|------------------|
| `kings_cross_euston_road_noisy` | `Kings Cross` |
| `wapping_pub_quiet_aircraft` | `Wapping` |
| `fabric_day_night_pattern` | `Farringdon` |
| `fulham_residential_quiet` | `Parsons Green` |

3. Filters search matches to `radiusMeters` using local `haversineMeters`, adds `distanceMeters`, sorts nearest-first.

Response fields when fallback is used:

- `sourceEndpoint`: `tfl.stopPoint.search`
- `fallbackFrom`: `tfl.stopPoint.getByGeoPoint`
- `fallbackReason`: upstream 404 message
- `searchQuery`: query string used

Route: `GET /api/discovery/tfl/nearby-stops?lat=…&lng=…&radiusMeters=…&testPointId=…&searchQuery=…`

## 6. Limitations of fallback

- Name search is not equivalent to radius geo search — results depend on station naming and `maxResults` cap (20).
- Without `searchQuery` or known `testPointId`, the route still returns 502 when geo is down.
- `returnLines: true` is not available on search matches; line data would require a follow-up `stopPoint.get(id)` call per stop.
- Re-test geo endpoints periodically; remove fallback path once `StopPoint_GetByGeoPoint` recovers.
