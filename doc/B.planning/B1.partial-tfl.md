### Direct tfl-ts verification (also fails)

```bash

const c = new tfl.default({ maxRetries: 0 });
await c.stopPoint.getByGeoPoint({
  lat: 51.5308, lon: -0.1238, radius: 500, returnLines: true,
  stoptypes: ['NaptanMetroStation','NaptanPublicBusCoachTram','NaptanRailStation']
}).then(r => console.log(r.stopPoints?.length)).catch(e => console.log(e.message));
"
```

Also tested from local `tfl-ts@2.2.0` source via `raw.stopPoint.getByGeoPoint` — same 404.

Raw TfL URL (redacted credentials):

```
GET https://api.tfl.gov.uk/StopPoint
  ?location.lat=51.5308&location.lon=-0.1238&radius=500
  &returnLines=true
  &stopTypes=NaptanMetroStation,NaptanPublicBusCoachTram,NaptanRailStation
```

Response: `{ "statusCode": 404, "message": "Resource not found" }`

### Related upstream failures

These geo endpoints also return 404 today (not a Next.js issue):

- `place.getByGeo` (including `BikePoint` type from tfl-ts playground demo)
- `GET /Place?placeGeo.lat=…&placeGeo.lon=…&radius=…`

Working alternative for manual discovery only:

```bash
curl "https://api.tfl.gov.uk/StopPoint/Search?query=Kings%20Cross&app_id=…&app_key=…"
```

Returns matches with `id`, `name`, `lat`, `lon`, `modes` — but is name-based, not radius geo search.

### Issues

1. **TfL geo lookup endpoints appear broken or deprecated** — `StopPoint_GetByGeoPoint` and `Place` geo both return 404 regardless of `stopTypes`, `modes`, or bounding box.
2. **OpenAPI marks `stopTypes` as required** — our helper now passes default stop types; did not fix the 404.
3. **tfl-ts array serialization** — `stopTypes` sent as comma-joined string; OpenAPI specifies `collectionFormat: multi`. Unlikely root cause since manual multi-param curl also 404s.
4. **Missing bundle fields** — cannot produce `stopPointId`, `commonName`, `modes`, `lines`, `distanceMeters` until geo endpoint works.

### Recommended fixes

1. **Short term:** treat TfL nearby stops as optional enrichment; core scoring must not depend on it (per B1 success criteria).
2. **Fallback:** add a separate discovery endpoint using `stopPoint.search` keyed by station name from geocoder output (lower precision, not radius-based).
3. **Monitor TfL API:** re-test `GET /StopPoint?location.lat=…` periodically; file issue with tfl-ts if geo endpoints recover but wrapper still fails.
4. **Upgrade tfl-ts** to `2.2.0` when geo is stable — current install is `2.1.0`.
5. **If geo recovers:** map response to bundle features with local distance/bearing recomputation from test-point lat/lng.

```json
        }

    }

```

HTTP 200. Latency ~200–400 ms.

### Fields confirmed

| Field | Present |
|-------|---------|
| `source` | yes |
| `sourceEndpoint` / `tflEndpointUsed` | yes |
| `retrievedAt` | yes |
| Line `id`, `name`, `modeName` | yes |
| `lineStatuses[].statusSeverityDescription` | yes |
| Disruption detail (`reason`, `disruption`) | yes with `detail: true` |

### Issues

- Large payload when `detail: true` — fine for discovery, may need trimming for production bundle.
- Line status is contextual (disruptions), not a direct noise proxy — P1.5 enrichment only.

### Recommended fixes

- For merged bundle: extract `{ lineId, lineName, severity, description }` only; omit nested route geometry.
- Optionally add `modes=tube` query param wrapper for tube-wide status board.
